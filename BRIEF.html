Payers deny claims for many reasons; providers lose revenue when denials aren't appealed well. Writing a strong appeal means matching denial reason to evidence in the record.

Domain primer — read this first

You are not expected to know this industry. This explains it in plain English.

In plain English
Insurers deny some provider claims, and providers lose money when denials aren't appealed well. A strong appeal matches the denial reason to evidence in the record. You're building the assistant that analyses a denial and drafts a grounded, evidence-backed appeal letter — citing only real record facts, with a specialist finalising it.
The people in this story
  • Revenue-cycle / billing specialist
  • Provider office manager

Worked example — one trip through the system

Concrete walkthrough
A claim is denied 'not medically necessary'. The tool identifies the evidence needed, pulls from the record ('two prior conservative treatments failed; imaging shows X'), and drafts an appeal citing each fact. The billing specialist reviews, tweaks, and sends. No clinical claims are made up.

09

AI engineering

The AI requirement
Denial classification + grounded appeal drafting that cites only real record evidence (no made up clinical claims). Guardrail: specialist finalises. Eval denial-reason accuracy + appeal groundedness on sample denials.
Keep it lean — you have 4 days. You're reusing your Foundation app, so the login, dashboard and basic API are already done. Spend the time on the AI core. Build one happy path really well + the AI core + a small eval + the safety check. Don't gold-plate. Each layer below is a small slice, not a production build.

You should still touch each layer below — it's what you trained on — but a lean version of each is fine:

Join the parts into one simple pipeline
Use LangGraph to connect the parts into one clear flow — a few nodes is plenty. Put a limit on every loop and retry.
Use a fixed data shape at every step
Pass data between parts in a fixed Pydantic shape. Check every AI output; fix or reject it if it's wrong.
Keep the run's state
Save the run's state (LangGraph state) so a step can resume. A simple store is fine — no fancy memory needed.
Knowledge base + good search
If the project uses RAG: load the knowledge base into Chroma with LangChain, search by keyword and by meaning, and show where each answer came from. Re-ranking is a nice-to-have.
A small test set for the AI
Make a small golden set — about 6–10 examples with the right answers — and score your AI on it (RAGAS for RAG). Show the score.
Fail the run on bad scores
If the score is below your bar, the run fails. A broken AI must not pass quietly.
A quick safety check
Run a short prompt-injection check (about a dozen prompts with PyRIT or garak) and mask obvious PII with Presidio. For risky steps, wrap the AI in fixed rules so it never makes the dangerous choice alone.
See what it's doing
Trace the main steps with OpenTelemetry (view in Jaeger, or just the console to start): prompt, time and cost. Add a backup for when the model is busy.

Build path — four days

DAY 1Understand & define
  • Read this brief + the domain primer until the problem is clear. List every unclear point as a question.
  • Write the PRD: scope with MoSCoW + RICE, lay it out Now / Next / Later, cut an honest MVP.
  • Lock the 2–3 success metrics (below). Write user stories with testable acceptance criteria as GitHub issues.
  • Sketch the UX: the primary journey + screen states (empty / loading / error / success).
Gate: PRD + prioritised backlog + wireframes reviewed. Scope signed off before code.
DAY 2Reuse base, design data & backend
  • Branch from your Foundation app (React + Node + JWT login/registration/dashboard). Reuse auth, structure, middleware — do not scaffold fresh.
  • Design the data model (ERD + schema) from the entities below. Normalise. Handle PII.
  • Write the OpenAPI contract. Build the core endpoints with validation, structured errors, logging and JWT.
  • Stand up the component skeleton from the architecture — stub each part behind a typed contract.
Gate: ERD + API contract + working auth'd endpoints reviewed.
DAY 3Frontend + the AI core (lean)
  • Build the React screens against the real APIs with honest loading/error states (reuse your dashboard shell).
  • Build the AI core: a few-node LangGraph wiring the parts, Pydantic schemas, bounded retries.
  • Where RAG is used: seed the Chroma KB, retrieve + cite on every answer (re-rank optional).
  • Add grounding + the deterministic safety wrapper. Start a small golden set (6–10 cases).
Gate: A working vertical slice — requirement → UI → API → data → AI output, grounded and checked.
DAY 4Harden, check & present
  • Integration + negative + authorization/isolation tests.
  • Score the golden set (RAGAS for RAG); wire the eval-gate. A quick injection check (PyRIT/garak) + PII masking (Presidio).
  • Basic OpenTelemetry trace of the main steps. README + architecture notes. Confirm issue→commit traceability.
  • Rehearse. Demo end-to-end + system-design viva.
Gate: Final demo + viva. Eval + safety results shown. Repo + traceability walked.

15

Ground rules

Open-source only — local LLM via Ollama, open embeddings, open vector DB. No paid keys, no secrets in the repo.
Reuse the open code you already built in the Foundation. Don't re-earn marks for boilerplate.
Synthetic data only. No real customer / patient / financial PII, ever.
The AI must be grounded — cite sources, refuse when unsupported, never make up facts or figures.
Safety-critical flows wrap the LLM in deterministic rules — the model never makes the dangerous call alone.
Bound every loop and retry. Trace it and gate it — failing evals fail the run.
Traceability is graded: every requirement → a GitHub issue → commits that reference it.
MIT-licensed — use it, change it, keep your work.
